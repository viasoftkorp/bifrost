Any OIDC issuer can be a **Generic OIDC** [trusted issuer](/enterprise/workload-identity/trusted-issuers). That covers services that already authenticate with an identity provider's **client-credentials** flow, such as Okta, Auth0 and Keycloak, and platforms that hand their workloads an OIDC token, such as a Kubernetes cluster or GitHub Actions.

You choose the issuer's **workload ID claim**: the claim whose value names a workload, usually the client ID or `sub`. When you map a workload, you enter that claim's value exactly as the token carries it, including case.

| Provider | Issuer URL | Workload ID claim | Rule, only to map the SSO app's client ID |
|---|---|---|---|
| Okta | The authorization server's issuer, e.g. `https://acme.okta.com/oauth2/default` | `cid` | `cid` equals the token's `sub` |
| Auth0 | Your tenant domain with a trailing slash, e.g. `https://acme.us.auth0.com/` | `azp` | `gty` equals `client-credentials` |
| Keycloak | The realm URL, e.g. `https://sso.acme.com/realms/acme` | `azp` | `preferred_username` starts with `service-account-` |
| GitHub Actions | `https://token.actions.githubusercontent.com` | `sub` | Not needed |
| Kubernetes | The cluster's service account issuer, exactly as tokens carry it in `iss` | `sub` | Not needed |

Bifrost takes a token from a generic issuer only when its workload ID is mapped to a service account. Every other token, including your people's when the same provider runs your SSO, goes through the normal sign-in path untouched. You need a rule only to map your SSO app's own client ID; see [Tell people's tokens apart](/enterprise/workload-identity/trusted-issuers#tell-peoples-tokens-apart).

## Prerequisites

- A Bifrost service account with an access profile for the workload.
- In Bifrost, **User Provisioning → Update** to add the issuer, and **User Provisioning → `UpdateWorkloadIdentities`** to map workloads.

## Step 1: Make tokens addressed to Bifrost

For providers with a **client-credentials** grant, configure the provider so tokens for your services carry Bifrost as their audience:

- **Okta:** use an authorization server whose audience is Bifrost's URL, and a scope your service apps may request.
- **Auth0:** create an API whose identifier is Bifrost's URL, and authorize your machine-to-machine apps for it.
- **Keycloak:** add an audience mapper that puts Bifrost's URL in `aud` for the service-account clients.

Workloads on a Kubernetes cluster or in GitHub Actions don't use a grant; they ask their platform for a token with Bifrost as the audience:

- **Kubernetes:** mount a projected service account token with `audience` set to Bifrost's URL (a `serviceAccountToken` source in a `projected` volume). Its `sub` is `system:serviceaccount:<namespace>:<service account>`, the value you map. The cluster's issuer must serve its discovery document and signing keys where Bifrost can reach them, as the managed OIDC issuers of EKS, AKS and GKE do.
- **GitHub Actions:** give the job `permissions: id-token: write` and request the token with Bifrost's URL as the audience. Its `sub` names the repository and ref, such as `repo:acme/payments:ref:refs/heads/main`.

## Step 2: Add the provider as a trusted issuer

1. In Bifrost, open **Governance → User Provisioning**, select the gear on the **Connection** card, and scroll to **Workload identity**.
2. Under **Additional trusted issuers**, select **Add issuer**, give it a name, and choose **Generic OIDC**.
3. Paste the issuer URL, set **Audiences**, and fill in **Workload ID claim** from the table above.
4. Select **Test**, then save the provider.

Once workloads are mapped on the issuer, its URL and workload ID claim can't change: see [how mappings follow an issuer](/enterprise/workload-identity/trusted-issuers#how-mappings-follow-an-issuer).

## Step 3: Map a client to a service account

1. Open the service account under **Governance → Users** and go to **Workload identities**.
2. Select **Add workload identity** and choose the issuer under **Token from**.
3. Enter the value of the issuer's workload ID claim as **Workload identifier**: the client ID for Okta, Auth0 and Keycloak, or the `sub` value for Kubernetes and GitHub Actions.
4. Select **Add**.

<Frame caption="Mapping a GitHub Actions workflow on the main branch to a service account.">
  <img src="/media/workload-identity/add-workload-oidc.png" alt="Add workload identity form with Token from set to GitHub Actions, workload identifier repo:acme/payments:ref:refs/heads/main and name payments deploy workflow" />

If the value is your SSO app's client ID and the issuer has no rule, Bifrost refuses the mapping and asks you to add the rule first.

## Step 4: Call Bifrost

The service sends its token as the bearer token.

<Tabs>
  <Tab title="Client credentials (Auth0)">
With a client-credentials provider, the service gets the token from the grant first. With `CLIENT_ID` and `CLIENT_SECRET` exported in the environment, the request body is built from the environment and sent on standard input, so the secret never appears in a command's arguments, where other users on the host could read it:

```bash
TOKEN=$(jq -n '{grant_type: "client_credentials", client_id: env.CLIENT_ID, client_secret: env.CLIENT_SECRET, audience: "https://bifrost.example.com"}' \
  | curl -s -X POST https://acme.us.auth0.com/oauth/token -H "Content-Type: application/json" --data-binary @- \
  | jq -r .access_token)

curl https://bifrost.example.com/v1/chat/completions \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model": "openai/gpt-4o-mini", "messages": [{"role": "user", "content": "Hello"}]}'
```
  </Tab>
  <Tab title="GitHub Actions">
```yaml
name: Call Bifrost

on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  call-bifrost:
    runs-on: ubuntu-latest
    steps:
      - name: Get a token for Bifrost
        id: oidc
        uses: actions/github-script@v7
        with:
          script: core.setOutput("token", await core.getIDToken("https://bifrost.example.com"))
      - name: Call Bifrost
        env:
          TOKEN: ${{ steps.oidc.outputs.token }}
        run: |
          curl https://bifrost.example.com/v1/chat/completions \
            -H "Authorization: Bearer $TOKEN" \
            -H "Content-Type: application/json" \
            -d '{"model": "openai/gpt-4o-mini", "messages": [{"role": "user", "content": "Hello"}]}'
```
A push to `main` in `acme/payments` gets a token whose `sub` is `repo:acme/payments:ref:refs/heads/main`, the value mapped in Step 3.
  </Tab>
  <Tab title="Kubernetes">
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: payments-worker
  namespace: payments
spec:
  serviceAccountName: payments-worker
  containers:
    - name: app
      image: acme/payments-worker
      volumeMounts:
        - name: bifrost-token
          mountPath: /var/run/secrets/bifrost
  volumes:
    - name: bifrost-token
      projected:
        sources:
          - serviceAccountToken:
              path: token
              audience: https://bifrost.example.com
              expirationSeconds: 3600
```
The app reads `/var/run/secrets/bifrost/token` on each call, since the kubelet rotates it, and sends it as `Authorization: Bearer <token>`. Map `system:serviceaccount:payments:payments-worker`.
  </Tab>
</Tabs>
